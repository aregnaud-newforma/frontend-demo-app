# ASP.NET Core and EF Core behind the API

ADR 0001 put Postgres behind the account API and reached it from a Node
process through Drizzle. The API is now a .NET process: ASP.NET Core minimal
APIs in `server/Api/`, over Postgres through Entity Framework Core and Npgsql,
with migrations generated by `dotnet ef`, committed, and applied by the API
when it starts. Sentry reports it through `Sentry.AspNetCore`, into the same
`frontend-demo-api` project the Node version used.

The frontend is unchanged. The contract the browser and the E2E specs depend
on - `/api/account`, the `/__test__/account` seeding route, `/health`, the
`e2e-session` cookie and `x-e2e-session` header, the JSON shape, port 3001 -
is the same on both sides of this decision, which is what makes it one the
frontend never has to know about.

## Why

The repository demonstrates the stack a product would ship, and the products
this frontend is a demo for run .NET behind their APIs. A Node backend was the
smallest thing that let the E2E tier talk to something real; it was never the
thing the frontend would actually face, and every rule about the boundary -
what the proxy forwards, how a trace crosses it - was being shown against a
process that does not exist in production.

## Considered options

- **Dapper with hand-written SQL.** Closest to what the Drizzle store read
  like, and the lightest dependency. Rejected because it has no migration
  tooling: the committed, generated, applied-at-startup migration flow that
  0001 chose would have to be rebuilt by hand, and that flow is the part worth
  demonstrating.
- **EF Core with Npgsql.** Chosen. `dotnet ef migrations add` is what
  `drizzle-kit generate` was, `Database.MigrateAsync()` at startup is what
  `migrate()` was, and the model is declared in code the way the Drizzle
  schema was. The mapping in `AccountsDb.cs` keeps the table and column names
  the Node migration created, so the SQL did not change when the language did.
- **Keeping Sentry's Node SDK conventions.** Not an option, but worth stating
  what moved: the `--import` ordering problem that gave the Node version its
  own `instrument.ts` does not exist here, since `UseSentry` wires the SDK into
  the host before any request is served; the manual `captureException` and
  span rename in `api.ts` are what the ASP.NET Core middleware does by itself.

## Consequences

- `dotnet` (SDK 10, pinned by `global.json`) is required alongside Node.
  `yarn api:start` is `dotnet run`, `yarn api:test` is `dotnet test`, and
  `yarn verify` ends on `dotnet build`. CI installs it with `setup-dotnet`.
- `DATABASE_URL` keeps its name and changes its form: Npgsql reads
  `Host=...;Username=...` and not a `postgres://` URL. `.env.example` and
  `ci.yml` carry the new value.
- The migration history table is EF's `__EFMigrationsHistory`, not Drizzle's
  `__drizzle_migrations`. A local database created by the Node version has the
  `accounts` table but no EF history, so its first `yarn api:start` fails on
  `CREATE TABLE accounts`; `docker compose down -v` once and it starts clean.
- The store's tests run under xunit against a Postgres that Testcontainers
  starts for the run. PGlite, which let the Node tests run with no service,
  has no .NET equivalent; the container is the next smallest honest Postgres,
  and Docker was already required by `compose.yaml`. They are their own tier
  (`yarn api:test`), not part of `yarn test`.
- `server/` is a .NET solution, so it leaves `tsconfig.json`, the Vitest
  `unit` project and the JS toolchain. The `@sentry/node`, `drizzle-orm`,
  `drizzle-kit`, `pg` and `@electric-sql/pglite` packages are gone.
- The evals in `evals/tasks.ts` that ask for a change to `server/api.ts` name
  a file that no longer exists; they need new subjects before the next run.
