# Postgres and Drizzle behind the API

`server/api.ts` keeps its accounts in a Map and forgets them when the process
dies, which is enough for the E2E tier and nothing else. Account Activity (#1)
is the first feature whose data has to outlive a restart, and this repository
exists to show the stack a real product would run, not the smallest thing that
works. So the API stores its data in PostgreSQL, reached through Drizzle ORM
over the `pg` driver, with migrations generated by `drizzle-kit`, committed, and
applied by the API when it starts.

## Considered options

- **`node:sqlite` with raw SQL.** Built into Node 22, no dependency, no service
  to run. Rejected because it is the answer to "smallest", and the demo is
  asked to answer "what would we ship". It would be replaced the day someone
  read the code as a template.
- **Drizzle over `node:sqlite`.** Same schema and migration tooling without a
  service. Rejected because the driver only exists in the Drizzle 1.0 release
  candidate, and because a Drizzle schema is written per dialect
  (`sqlite-core` versus `pg-core`): moving to Postgres later would mean
  rewriting the schema, not swapping a connection string.
- **Prisma.** Better migration tooling and a data browser. Not chosen because
  Drizzle infers its types from the TypeScript schema with no generate step,
  stays close to the SQL it emits, and is the lighter dependency. Either would
  have worked; this is a preference for SQL-shaped code, not a verdict on
  Prisma.

## Consequences

- Postgres is required for `yarn dev` and `yarn e2e`. Locally it comes from
  `compose.yaml`; in CI the e2e job declares a `postgres` service. The
  connection string is `DATABASE_URL`, documented in `.env.example`.
- The store is unit-tested in the Node tier against PGlite, Postgres compiled
  to WebAssembly, so those tests need no service. The integration tier keeps
  MSW at the network boundary and never sees a database.
- `server/` stays flat: `db.ts` (connection and startup migration),
  `schema.ts` (tables), `store.ts` (queries), `migrations/` (generated SQL).
  It becomes verticals only when a second subject unrelated to the Account
  appears.
- Imports run one way: `server/` may import pure helpers and types from
  `src/account/helpers/`; nothing under `src/` imports from `server/`.
- The per-session key that isolates parallel E2E specs stays, now as a column
  rather than a Map key.
- `drizzle-orm` is pinned to the 0.45 stable line until 1.0 ships.
